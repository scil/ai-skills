# AI 提示工作流

如何使用 AI 工具（Claude、v0、Figma AI）实际生成温情产品界面，同时不陷入通用 SaaS 风格。这是一份工作流文档——每次用 AI 生成页面或组件时都应参考。

## 核心问题

AI 工具在整个互联网上训练，这意味着它们的默认输出反映的是**平均 SaaS 审美**——白色背景、Inter 字体、蓝色主按钮、"提交"文案。没有约束，它们会把每一个温情产品都退化成通用 SaaS 仪表盘。

解决方案是在每个提示词中**前置约束**——设计令牌、词汇替换表和情感简报。有了这些约束，AI 工具就成了有用的协作者；没有它们，它们会把设计拉向均值。

## 三提示词工作流

对任何页面或组件，按顺序使用三个提示词——每个来自不同的工具，每个做它最擅长的事。

### 提示词一：Claude——写"情感脚本"

在做任何视觉生成之前，让 Claude 为这个页面写**情感状态脚本**。这*不是*功能说明书。

示例提示词：

```
对于一款以门廊命名的温情产品（一个温情的关系型产品，用户与邻居分享资源），
请为"感谢时刻"页面写情感脚本。

情感脚本应该描述：
- 用户到达这个页面时的情感状态
- 我们希望他们离开时带走的一种感受
- 他们需要按什么顺序看到什么
- 他们不应该看到什么
- 页面上最重要的单一 UI 元素，以及原因

不要描述颜色、字体、布局网格或具体组件。
只描述情感逻辑。
```

Claude 会返回类似这样的内容：

> 用户是分享者。他们帮助过的人刚刚确认收到了资源。用户到达时的状态是中性的好奇——他们收到了一条通知，点进来了。我们希望他们离开时的状态是"感受到温暖"——一种真实的、自己做了有意义的事情的小小感觉。
>
> 他们首先需要看到的：收到方留的便条。不是姓名，不是资源，是便条。便条才是礼物。其他一切都是背景。
>
> 他们其次需要看到的：是谁写的（小头像、姓名）。这让信息有了落点。
>
> 他们不应该看到的：任何"分享出去！"的行动呼吁，任何数据（"你这个月已经给了 3 份礼物"），任何做更多事的提示。这个时刻是神圣的——让他们停留在其中。
>
> 最重要的单一 UI 元素是收到方的便条，用手写字体渲染，字号大，居中，周围有负空间。其他一切都是配角。

这份脚本现在成为后续两个提示词的**简报**。

### 提示词二：Claude——用约束生成规格说明

现在让 Claude 把情感脚本翻译成具体的组件规格，并使用设计令牌和词汇替换表。

示例提示词：

```
使用门廊示例的设计令牌 [粘贴令牌] 和词汇替换表 [粘贴表格]，
将这份情感脚本 [粘贴提示词一的输出] 翻译成 v0 可用的具体组件规格。

输出应包含：
- 布局结构
- 每个元素的具体令牌（背景色、文字色、字体、圆角、阴影、间距）
- 任何文字的精确文案（使用词汇替换表）
- 所需的交互
- 不应该包含什么的说明

不要包含任何十六进制色值、字体名称或像素值——只用令牌引用。
```

Claude 会返回一份包含令牌名称的结构化规格说明。这就是发给 v0 的内容。

### 提示词三：v0——生成实现

现在把规格说明交给 v0，以令牌作为第一个约束：

```
使用以下设计令牌构建一个 React 组件。你必须对所有颜色、字体、
圆角、阴影和间距值使用 var(--令牌名)。不要硬编码任何视觉值。

设计令牌：
[粘贴完整的 tokens.css]

组件规格：
[粘贴提示词二的输出]

约束：
- 只使用映射到令牌的 Tailwind 工具类，或内联 var() 样式
- 标题的 serif 字体使用 Lora（--font-heading）
- 正文使用 DM Sans（--font-body）
- 仅在规格说明指定手写字体的地方使用 Caveat（--font-handwrite）
- 背景必须是 var(--color-background)，不用白色
- 按钮必须是 var(--color-primary)，白色文字，圆角 var(--radius-md)
- 不用填充图标——只用描边（使用 lucide-react）
```

v0 生成组件。因为令牌约束了它，输出是符合品牌的，而不是通用的。

## 为什么是三个提示词而不是一个

诱惑是把所有东西一次性发给 v0（"这是令牌，这是词汇，给我构建一个页面"）。这会失败，因为：

1. v0（和 Figma AI）擅长把规格说明转化为代码，但不擅长上游的创意思维
2. Claude 擅长情感逻辑和文案，但生成的视觉保真度较低
3. 分开工作能发挥每个工具的优势

三个提示词还在每个阶段创造了**审查检查点**。你可以在提交规格说明之前纠正情感脚本，在生成代码之前纠正规格说明。没有检查点，错误会累积。

## 令牌提示词前缀

对于任何 v0 或 Figma AI 生成请求，准备一个**标准前缀**，在每次提示词开头粘贴。这个前缀从不变化，所以可以可靠地复制粘贴。

模板前缀：

```
你正在为 [产品名称] 设计组件，这是一款 [一句话定位]。

必须使用的设计令牌（用 var(--名称)——永远不要硬编码）：

[在此粘贴完整的 tokens.css]

必须使用的词汇（生成文案时精确使用这些措辞）：

[粘贴相关的词汇替换表行]

必须遵守的约束：
- 背景用 var(--color-background)——永远不用白色
- 正文行高 1.7
- 按钮：主要操作使用 var(--color-primary)，圆角 var(--radius-md)
- 图标：仅用描边（lucide-react、Tabler 描边版或 Phosphor regular）
- 字体：标题用 var(--font-heading)，正文用 var(--font-body)
- 不用填充图标，不用 Inter/Roboto 字体，不用 rgba(0,0,0,...) 阴影
- 所有界面文字用句子大小写，永远不要首字母大写

需要避免的反模式：
[列出 3 个产品专属反模式]

现在请构建以下内容：
[组件描述]
```

在每次新组件请求前粘贴这个前缀。第一个提示词建立约束；后续每个提示词都应该重新粘贴，因为聊天记忆会漂移。

## 生成后的迭代

当 v0 返回的输出接近但有漂移时，**不要要求笼统的修改**。要求特定令牌的修改。

- ❌ "让它感觉更温暖"
- ✅ "把 bg-white 类替换成 style={{background: 'var(--color-background)'}}，把标题的 font-sans 改成 font-serif"

具体的、令牌引用的纠正有效。模糊的语气反馈无效，因为 AI 不知道该转哪个旋钮。

## AI 常见失败模式及纠正

| 失败表现 | 原因 | 纠正提示词 |
|---|---|---|
| 用了 `bg-white` 而不是令牌 | Tailwind 默认值 | "把 bg-white 替换成 bg-[var(--color-background)] 或内联 style" |
| 用了 Inter 字体 | 最常见的训练默认值 | "把 font-family 改成标题用 var(--font-heading)，正文用 var(--font-body)" |
| 用了填充图标 | 默认 Lucide 图标是混合的 | "把所有填充图标变体替换成描边版本（例如把 HeartIcon 换成 lucide-react 的描边 Heart）" |
| 用了"提交"文案 | 表单惯例 | "把'提交'换成 [词汇替换表中的对应项]。把'取消'换成 [对应项]。" |
| 用了首字母大写 | 常见的样式预设 | "全部改用句子大小写——每个标签只有第一个词大写" |
| 用了 rgba(0,0,0,...) 阴影 | Tailwind 默认值 | "把阴影颜色替换成 var(--shadow-card) 引用" |
| 用了硬编码十六进制值 | 直接写十六进制对 AI 来说更容易 | "把每个十六进制值替换成令牌中对应的 var(--color-*) 引用" |
| 用了计数通知（"3 条新消息"） | 通用 SaaS 模式 | "把通知改写为'X 个人在等你'或类似表达——参见词汇替换表" |

## 什么时候不用 AI 生成

适合用 AI 的情况：
- 从规格说明生成组件结构
- 起草文案变体
- 把情感脚本转化为布局
- 生成样板代码（表单、列表等）
- 生成说明性 SVG

不应该用 AI 的情况：
- **原始情感脚本** — 这是人的判断，AI 可以帮助表达，但不应该由 AI 原创
- **隐喻提取** — 需要人的品味和产品知识
- **词汇替换表** — 需要人大声读出每一行，接受或拒绝
- **选择品牌配色** — AI 建议往往趋向于训练集中的均值调色盘；人的筛选很重要
- **审查最终结果** — 自动化检查会遗漏情感漂移这个核心问题

## 专门与 Claude 合作

Claude（本助手）特别适合：
- 撰写情感简报
- 提取隐喻
- 生成词汇替换建议
- 从样式决策中产出设计令牌文件
- 审查 v0 输出是否偏离了约束

向 Claude 请求这些时，提供：
- 产品定位段落
- 任何已经做出的决策（令牌、文案）
- 你想要的具体输出格式

Claude 不太适合：
- 生成像素级精确的视觉 mockup（用 Visualizer 做草图，用 v0 做代码）
- 生成 Figma 文件（直接用 Figma AI）
- 生成摄影或插图（用图像生成工具，但在提示词中明确写入温情产品的反模式）

## 保存产出物

在项目生命周期中，在 `design-system/` 文件夹中积累这些产出物：

```
design-system/
  emotional-brief.md           ← 阶段一的产出
  metaphor-map.md              ← 阶段二的产出
  vocabulary.md                ← 阶段三的产出
  style-guide.md               ← 阶段四的产出（填写完整的模板）
  tokens.css                   ← 阶段五的产出（实际代码）
  emotion-scripts/             ← 每个页面一个
    landing.md
    empty-state.md
    thank-you.md
    request-dialog.md
    notification.md
  prompts/
    v0-prefix.txt              ← 标准令牌+词汇前缀
```

这让设计系统可以被重现，让新的贡献者（人或 AI）能够快速上手。
