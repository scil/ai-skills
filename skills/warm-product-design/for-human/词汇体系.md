# 词汇体系

一套在整个产品中系统性地用关系型语言替换事务型语言的方法。这是**杠杆最大**的设计干预——零成本，无需修改任何代码，却能彻底改变用户在每个页面的情感体验。

## 核心原则

产品的语言在训练用户如何与它相处。当一个按钮说"提交"，用户就是在填表。当它说"轻声询问"，他们就是在对话。功能结果完全相同；情感结果截然相反。

通用 SaaS 词汇（"提交"、"取消"、"待处理"、"接受"、"拒绝"、"资料"、"仪表盘"、"通知"）是为生产力工具和电商设计的。在温情型/关系型产品中使用它们是**历史遗留**——它们存在是因为设计师在复制其他 App，而不是因为它们服务于这个产品。

## 替换规则

### 规则一：在情感时刻用关系型语言，其他地方用普通语言

不要试图让每一个标签都充满诗意。这种对比本身就是让温情时刻感觉温情的原因。

- **使用关系型语言的场合**：主操作按钮、通知、空状态、感谢页、欢迎界面、发起请求、接受/拒绝请求、状态指示器、关键旅程的页面标题。
- **保持普通语言的场合**：表单字段标签（邮箱、电话、地址）、设置开关、无效输入的错误信息、技术性确认（"已保存"）、没有好隐喻时的导航标签（这时就直接叫"设置"）。

如果每个词都充满诗意，产品会显得矫情，用户会失去信任。把诗意留给值得的时刻。

### 规则二：以人为先，而不是以动作为先

几乎所有事务型通知都可以通过先提到那个人来改写。

- "你有 3 条新请求" → "3 个人在等你回复"
- "请求已批准" → "Sarah 正在路上"
- "收到消息" → "Michael 给你留了一条便条"
- "新邀请" → "Ana 邀请你来她的门廊"

语法结构本身承载情感重量。以人为主语感觉像人；以系统为主语感觉像官僚机构。

### 规则三：用产品的隐喻作为词汇来源

如果已经完成了隐喻提取（见 `metaphor-extraction.md`），隐喻本身就提供了词汇。直接使用：

- 门廊：留便条、门廊灯亮着、在门廊放点东西、邻居来访过
- Hearth：拨弄、光晕、聚拢、余烬
- Lantern：点亮灯笼、变暗、提着、指引

如果一个替换能用隐喻的词汇完成，几乎永远都应该用——语言与视觉隐喻之间的对齐，正是创造出统一产品感受的东西。

### 规则四：用人替代计数

数字计数是市场平台的模式（"3 条消息"、"5 条未读"、"12 条待处理"）。温情产品用人情化的框架表达相同的信息。

- "3 条未读" → "3 个人在等你"
- "5 件商品在你的购物车" — 不适用，温情产品没有购物车
- "12 条待处理请求" → "12 位邻居希望听到你的消息"
- "0 条" → 用隐喻设计空状态（不要显示零）

### 规则五：让拒绝变得温柔

温情产品中最容易被忽视的机会是**拒绝流程**。大多数产品让拒绝显得粗暴，因为它们为效率而设计，不是为关系。

- "拒绝" / "不接受" → "这次不行，也许下次"
- "不了，谢谢" → "也许改天"
- 提供结构化的温柔理由："别人先到了" / "我不在城里" / "留给家人了"——让系统用温柔的语气自动发送这条信息。

当用户拒绝一个请求，请求方收到的信息应该**保护这段关系**。默认的"您的请求已被拒绝"听起来像公寓申请。"Sarah 说她留给家人了——也许改天"听起来像邻居。

### 规则六：空状态发出邀请，不施加压力

空状态是新用户决定是否值得投入的地方。默认模式（"你还没有添加任何内容！开始使用 →"）是在施压。温情产品的模式是将空状态描述为一个特征，而不是一个缺失。

- "你还没有添加任何资源！" → "你的门廊今天很安静。等你准备好了，可以放点东西出来。"
- "还没有伙伴——邀请朋友吧！" → "你的圈子还没有形成。人会慢慢来的。"
- "没有请求" → "清晨的宁静。"

转变在于：从"你应该做更多"到"现在这样也很好，更多的会在它该来的时候来"。

### 规则七：引导流程请求许可，不追求完成度

- "完善你的资料（3/5 步）" → "有空的时候，说说你自己"
- "验证你的邮箱" → "我们很乐意偶尔给你发封邮件——方便的时候确认一下邮箱"
- 引导流程中的进度条 → 去掉。它们把欢迎变成了清单。

## 替换对照表

对每个产品，在设计阶段建立一张完整的替换对照表，作为所有文案的权威来源。下面是 门廊示例的对照表，作为实战示例——对其他温情产品复制这个结构。

| 事务型（通用 SaaS） | 关系型（温情产品） | 出现位置 |
|---|---|---|
| 提交请求 | 在门廊留一张便条 | 请求流程的主操作按钮 |
| 接受 | 是的，它是你的 | 资源方的接受按钮 |
| 拒绝 | 这次不行，也许下次 | 资源方的拒绝按钮 |
| 待处理 | 等待回音 | 请求状态 |
| 已批准 | 正在路上 | 接受后的状态 |
| 你有 3 条请求 | 3 位邻居来访过 | 收件箱标题 |
| 通知 | 最近发生了什么 | 标题 |
| 资料 | 你的门廊 | 标签页/导航 |
| 仪表盘 | 主页（或直接是门廊视图） | 主屏幕 |
| 添加资源 | 在门廊放点东西 | 按钮 |
| 可用 | 门廊灯亮着 | 状态指示器 |
| 不可用 | 今天在里面 | 状态指示器 |
| 邀请链接 | 你的门廊地址 | 分享界面 |
| 好友 / 联系人 | 伙伴 / 邻居 | 列表标签 |
| 公开可见 | 从街上可以看到（已拒绝；改用 Porch Visible） | 隐私设置 |
| 私密 | 只有你 | 隐私设置 |
| 发送 | 发送（或"放在这里"） | 表单提交 |
| 提交评论 | 留一条便条 | 评论操作 |
| 评分 | —（完全去掉） | 不给人打分 |
| 评价 | 一封感谢便条 | 交易后操作 |
| 设置 | 设置（保持普通，不替换） | 导航 |
| 帮助中心 | 如果哪里不对劲 | 支持入口 |
| 注册 | 进来吧 | 新用户流程 |
| 登录 | 欢迎回来 | 老用户 |
| 退出登录 | 回头见 | 退出 |
| 删除账户 | 拆掉你的门廊 | 设置 → 危险操作区 |
| 错误：输入无效 | （保持普通——错误信息不应该可爱） | 表单验证 |

## 如何建立你自己的替换对照表

对每个新温情产品：

1. 列出产品中的每一个界面字符串（或主要流程中的所有字符串）
2. 识别哪些出现在情感时刻（规则一）
3. 对每个情感时刻的字符串，结合产品隐喻写出 2–3 个候选替换
4. 挑选大声读起来最自然的那个——如果一个短语对着朋友说出来会尴尬，就拒绝它
5. 通过阅读三个使用了新词汇的示例页面来测试对照表——如果听起来像在搞笑，那就收敛；如果听起来像一个稍微更有心的朋友，就对了

## 大声朗读测试

测试温情产品文案的最佳方法：**像对一个你尊重的朋友说话一样，大声读出来**。

- "请提交您的请求以获取此资源的访问权限。" — 不会这样说。拒绝。
- "想向 Sarah 问问那把椅子吗？" — 可以这样说。接受。
- "你的门廊今晚在发光！" — 过头了。拒绝（这是在搞笑，不是温情）。
- "你的门廊今天很安静。" — 可以这样说。接受。

"比典型 SaaS 更温暖"和"尴尬的矫情"之间的界线很细。大声朗读测试能捕捉两侧。

## 常见失败模式

- **矫情过度**：每个标签都有 emoji，每个空状态都有俳句，每条错误信息都像诗。结果：感觉在哄小孩。修复：把温情留给情感时刻，功能性文案保持普通。
- **语气不一致**：同一个流程里有些按钮说"在门廊留一张便条"，有些说"提交请求"。结果：感觉像两个产品粘在一起。修复：在上线前建立完整的替换对照表。
- **隐喻错配**：在不适合门廊隐喻的功能中强用门廊词汇（例如把设置菜单叫"门规"，但它实际上只是一堆开关）。结果：感觉生硬。修复：只在映射真实存在的地方做隐喻替换。
- **施压的空状态**：「你的门廊很安静——快去邀请朋友吧！」把所有功夫都白费了。修复：空状态必须发出邀请，不施加压力。如果必须有 CTA，让它小且次要。
- **冷漠的拒绝路径**：一个漂亮的请求流程，最后以"您的请求已被拒绝"结束，等于前功尽弃。修复：以同等的用心设计拒绝路径，通常要更用心。

## 与其他阶段的整合

词汇体系被以下环节使用：

- **风格指南**（`style-guide-template.md`）：按钮文字和示例界面字符串来自这里
- **页面设计**（原型、mockup、v0 提示词）：每个页面的文案都从这张表取用
- **AI 提示词**（`ai-prompting-workflow.md`）：替换对照表被纳入 v0/Figma AI 的提示词，使生成的页面从一开始就使用正确的词汇

早点建立这张表。每当设计新流程时更新它。把它当作一个有版本的产出物，而不是一次性的练习。
